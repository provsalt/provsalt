はい、自分でも分かっています。前回のAI記事は[AIの現状と、私がそれを嫌う理由](https://raymond.moe/ja/blog/why-ai-usage-has-become-problematic)でした。そんな私が今度は、机に置ける小さなコンピューターで1800億パラメータのモデルを動かすために、かなりの時間を溶かしています。

AIを、何でも解決してくれる魔法のように製品へ載せる風潮は今でも嫌いです。でも、どう考えても大きすぎるモデルを、ぎりぎりのハードウェアで動かすための工夫は好きです。

[Qwen3.8-Flash-Next](https://huggingface.co/Qwen/Qwen3.8-Flash-Next)は、QwenがQwen4向けに開発しているアーキテクチャの早期プレビューです。メインモデルは1250億パラメータで、1トークンあたり約60億パラメータが動きます。そこに40億パラメータのMTPヘッドも付いています。それでも足りなかったのか、さらに510億パラメータのn-gram埋め込みテーブルまで載っています。

公式safetensorsに入っている値を正確に数えると179,999,981,459個です。180Bモデルと呼んでよいでしょう。今回の変換では、その全部を残しました。Hugging Face上の表示が約93Bなのは、パックされたNVFP4のバイト列とスケールから、論理上のパラメータ数をうまく計算できないためです。

## なぜチェックポイントがこんなに大きいのか

n-gramテーブルはPosition-Learning Enhancement、略してPLEと呼ばれています。幅2,560のbigramとtrigramの行が約2000万あります。リクエストを処理するとき、Qwenが参照するのはそのうち数行だけです。512億個の値を全部掛け算しているわけではありません。

510億ものパラメータを密なレイヤーとして計算せずに、モデルの容量だけ増やせる。かなり賢いやり方です。ただ、FLOPsを使わないパラメータもメモリはしっかり食べます。

ベースには[InferactのModelOpt NVFP4チェックポイント](https://huggingface.co/Inferact/Qwen3.8-Flash-Next-NVFP4)を使いました。最初は、通常のモデル重みが約135Bあり、そこへ51Bのn-gramテーブルを足した構成だと考えていました。チェックポイント全体のサイズは170.189 GiBです。

私の[DGX Spark](https://docs.nvidia.com/dgx/dgx-spark/hardware.html)には128 GBのユニファイドメモリしかありません。KVキャッシュもワークスペースも使わず、ついでにPythonもメモリを使わないようvLLMへ丁寧にお願いしたところで、170 GiBは入りません。

## 最初はREAPで削るつもりだった

真っ先に目を付けたのは、約135Bのメインモデルでした。NVFP4と名前に入っている以上、n-gramテーブルを含む大事な部分はすでに量子化されていると思っていました。そうなると、まだ縮められそうなのはMoEのエキスパートです。

最初の案は、エキスパートを25%削ることでした。REAPで枝刈りすれば、Sparkのメモリ上限を下回るだろうと考えたのです。

ところが、safetensorsのインデックスとPLEのシャードを開いてみると、前提が間違っていました。

InferactはモデルのバックボーンをNVFP4にしていましたが、n-gramテーブルには手を付けていません。512億個のPLE値はすべてBF16のままで、128個のシャードに分かれていました。このテーブルだけで102,400,491,520バイト、95.368 GiBあります。

削ろうとしていた部分はすでに圧縮済み。圧縮済みだと思っていた部分だけで約100 GiB。完全に逆でした。

これなら、モデルを入れるためだけにエキスパートを削る必要はありません。放置されていたPLEテーブルを量子化するだけで足りるかもしれません。

とはいえ、Qwenの新しい`qwen4_exp`アーキテクチャをREAPへ追加する作業はすでに始めていました。そこで、枝刈りに意味があるのかも測ることにしました。32個の混合キャリブレーションプロンプトと、別に用意した8個のホールドアウトプロンプトを使い、通常どおりPLEを動かした公式FP8モデルと次トークンの236地点を比較しました。

| 変更 | Top-1一致率 | 参照Top-1が候補Top-5に入る割合 | KLダイバージェンス | ロジットのコサイン類似度 |
|---|---:|---:|---:|---:|
| PLEだけNVFP4 | 91.525% | 100.000% | 0.015591 | 0.995399 |
| REAPだけ、25%削除 | 87.712% | 100.000% | 0.042569 | 0.991027 |
| REAPとNVFP4 PLE | 91.102% | 99.576% | 0.040298 | 0.990824 |

知りたかったのは、どの変更が元のモデルに一番近いかです。

PLEだけをNVFP4にしたモデルは、エキスパートを25%削ったモデルより参照モデルに近くなりました。REAPとNVFP4を組み合わせてもTop-1一致率は上がりません。KLダイバージェンスに至っては、PLEだけを変えた場合の2倍を超えています。

これで方針は決まりました。REAPは使いません。公開版ではエキスパートを一つも削らず、PLEテーブルの保存形式だけを変えています。

## PLEテーブルをBF16で持つ必要はない

PLEがしていることはテーブルの検索です。モデルの残りの部分が必要とするのは、選ばれた行のBF16データだけ。ほとんどの行がリクエスト中に一度も使われないのに、512億個の値をすべてBF16で展開しておく必要はありません。

そこで、PLEの値2個をNVFP4 E2M1で1バイトに詰めました。16個の値ごとにE4M3のブロックスケールを1個持たせ、元の128個のPLEシャードには、それぞれFP32のグローバルスケールを1個持たせています。

パックした値1個あたり0.5バイト、ブロックスケールにさらに16分の1バイトです。最終的にはBF16の3.5555分の1まで小さくなりました。

| 成果物 | 正確なバイト数 | GiB |
|---|---:|---:|
| 元のBF16 PLEテーブル | 102,400,491,520 | 95.368 |
| NVFP4 PLEテーブル | 28,800,138,752 | 26.822 |
| 元のチェックポイント全体 | 182,738,792,440 | 170.189 |
| 変換後のチェックポイント全体 | 109,138,439,672 | 101.643 |
| F16マルチモーダルプロジェクター付きUnsloth UD-Q4_K_XL GGUF | 112,238,658,784 | 104.530 |

バックボーンを変えず、エキスパートも削らずに68.546 GiB減りました。これでチェックポイントはDGX Sparkのメモリ上限に収まります。

実行時の流れは、だいたい次のとおりです。

~~~text
トークンID -> Qwenのn-gramハッシュ -> パックされた行を検索
           -> NVFP4からBF16へ展開 -> vLLMのGPUバッファ
~~~

PLEテーブル全体は、CPU側のメモリにパックしたまま置きます。プラグインが必要な行だけを取り出してBF16へ戻し、既存のvLLMコードへ渡します。Attention、MoE、サンプリング、スケジューリング、マルチモーダル処理はvLLM側の実装をそのまま使います。

## vLLMに入れるところが一番面倒だった

Qwen3.8-Flash-Nextは新しすぎて、通常のvLLMイメージにもPyPI版にもアーキテクチャが入っていません。NVIDIAが初日対応の専用vLLMイメージを出していたので、テストしたダイジェストへ固定しました。

Qwen4の正式公開までに何度も変わりそうなプレビューモデルのforkを、ずっと面倒見る気にもなれません。今回はPLEの埋め込みクラスだけを差し替える、vLLMの汎用プラグインにしました。

ここにも落とし穴がありました。vLLMはCPUへ逃がしたPLEテーブルを専用の子プロセスで動かしますが、そのプロセスは通常のプラグインを読み込みません。プラグイン側でPLEプロセスのエントリーポイントをラップし、子プロセスの中でも自分を登録してから、vLLMへ処理を戻すようにしました。

途中では、なかなか楽しいエラーにも遭遇しました。

テンソル並列サイズを1にすると、vLLMは単一プロセス用のexecutorを選びます。ところが、このexecutorはPLEワーカーを起動しません。そのため、GPUが1基しかなくてもサーバーには`mp` executorが必要です。

メモリが減るならと思い、FP8のKVキャッシュも試しました。Qwen Sparse Attentionからは、すぐにこう返されました。

~~~text
NotImplementedError: Qwen3.8-Flash-Next QSA requires a BF16 main KV cache
~~~

はい、分かりました。最終構成ではメインのKVキャッシュをBF16のままにしています。

## DGX Spark 1台で起動する

物理サイズ101.643 GiBのチェックポイントは、テンソル並列サイズ1でNVIDIA GB10 1基に読み込めました。

マルチモーダルをすべて有効にした状態では、モデル読み込み中の使用量が73.97 GiBと表示され、KVキャッシュには2 GiBが確保されました。26.822 GiBのPLEテーブルはCPUワーカー側に残ります。ただし、GB10のCPUとGPUは同じLPDDR5xの物理メモリを共有しています。APIの起動には約639秒かかりました。

APIサーバーを10分以上待つのはつらいです。でも、ちゃんと起動しました。

画像とテキストのリクエストを送った後、空きメモリは19.8 GiB、システム全体のスワップ使用量は14.0 GiBでした。入るには入ります。余裕はありません。

マルチモーダルのテストには、宇宙服を着ずに月面へ立つ人物の画像を生成して使いました。Qwenには、画像に何が写っているかを聞きました。

返ってきた3文の回答がこちらです。

## 速いのか

速くはありません。でも、使えないほどでもありません。

[llama-benchy](https://github.com/eugr/llama-benchy)をOpenAI互換のvLLMエンドポイントに対して実行しました。プレフィックスキャッシュと3トークンのMTP投機的デコードを有効にし、2,048トークンのプロンプト処理、128トークンの生成、最大100,000トークンのコンテキストを測っています。

| テスト | 同時実行数 | スループット |
|---|---:|---:|
| 2,048トークンのプロンプト処理 | 1 | 1,410.5トークン/秒 |
| 128トークン生成 | 1 | 24.1トークン/秒 |
| 128トークン生成 | 10 | 合計45.2トークン/秒 |
| 100,000トークンのコンテキスト構築後に生成 | 1 | 21.8トークン/秒 |

100,000トークンのコンテキストを作るだけで、生成前に約69.7秒かかりました。同時実行数10では合計45.2トークン/秒ですが、リクエスト1件あたりの平均は7.6トークン/秒しかありません。

最初のベンチマークはメモリ不足で落ちました。32 GiBのスワップファイルを別に追加し、サーバーを再起動してもう一度走らせたところ、今度は完走しました。スワップがあればマシンは耐えます。速くはなりません。長いコンテキストで同時実行数を増やすと、結果はかなり厳しいものでした。

作業を始める前から[Unsloth GGUF](https://huggingface.co/unsloth/Qwen3.8-Flash-Next-GGUF)のことは知っていました。4ビットのUD-Q4_K_XL版は、モデルファイルだけで103.688 GiB、F16のマルチモーダルプロジェクター込みで104.530 GiBです。今回の101.643 GiBとかなり近いサイズです。

違うのは動かし方です。Unsloth版はllama.cpp向けですが、私はすべてをNVFP4でそろえ、MTPも使いたかった。そのほうが速いだろうとも考えていました。

## ほかの人も使える形にする

全部を一つのHugging Faceリポジトリへ入れると収拾がつかないので、公開物は三つに分けました。

[Hugging Faceのモデル](https://huggingface.co/provsalt/Qwen3.8-Flash-Next-NVFP4-PLE-NVFP4)には、変換後の重み、tokenizer、設定、ライセンスだけを置いています。サイズは101.643 GiBで、InferactのNVFP4バックボーンには手を加えていません。

[GitHubリポジトリ](https://github.com/provsalt/qwen3.8-flash-ple-nvfp4)には、converter、vLLMプラグイン、Dockerfile、Compose設定が入っています。converterは途中から再開でき、完了済みのシャードも検証します。変更していないチェックポイントファイルはhardlinkにできるので、理由もなく74.8 GiBをもう一度コピーせずに済みます。

[公開GHCRパッケージ](https://github.com/users/provsalt/packages/container/package/qwen3.8-flash-ple-nvfp4)には、固定したvLLMランタイムとプラグインを入れました。ソースリポジトリへのリンクもあり、通常の`vllm serve`エントリーポイントをそのまま使えます。

公開したDGX Spark 1台用の構成は、Composeで起動できます。

~~~bash
git clone https://github.com/provsalt/qwen3.8-flash-ple-nvfp4
cd qwen3.8-flash-ple-nvfp4
docker pull ghcr.io/provsalt/qwen3.8-flash-ple-nvfp4:latest
VLLM_IMAGE=ghcr.io/provsalt/qwen3.8-flash-ple-nvfp4:latest \
  docker compose up --detach
docker compose logs --follow api
~~~

初回は100 GiBを超えるチェックポイントをダウンロードします。2分たっても起動しないからと、ターミナルを見つめ続けても早くはなりません。

エンドポイントはLiteLLMの後ろにも置きました。最初のリクエストは404でした。ベースURLに`/v1`を付け忘れただけです。ここまでの問題と比べると、あまりにも地味でした。直した後は、ほかのOpenAI互換モデルと同じように動いています。

## 最後に

PLEテーブルを変換し、そのチェックポイントを読み込み、テキストを生成し、画像と動画を処理し、DGX Spark 1台からvLLMで配信できました。比較結果もはっきりしています。今回試した25%のREAP枝刈りより、PLEだけをNVFP4にしたほうが参照モデルに近いままでした。

このプロジェクトは「REAPとNVFP4を使えば入るのか」から始まりました。結果は、その質問より少し面白いものになりました。

エキスパートは削らなくていい。メモリとして居座る巨大なテーブルを量子化すればよかったのです。

今でもAIの過剰な宣伝は嫌いです。それでも、こんな無茶なモデルをローカルで使えるのは正直すごい。GPT-3が公開された頃には、考えもしなかったことです。
